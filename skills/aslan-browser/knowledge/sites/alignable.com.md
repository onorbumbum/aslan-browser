# alignable.com

Business networking site. Requires an authenticated session (cookies in the browser).

## Group member lists

URL: `/biz/groups/<group-slug>/members`

- Renders **20 members** initially, then infinite-scrolls.
- `?page=N` is **ignored** — there is no page param.
- Load-more endpoint (fires on scroll):
  `/biz/groups/<group-slug>/members/list?except_ids=<csv-of-seen-ids>&filter=all`
  Returns an HTML fragment of **20 rows**, excluding `except_ids`. There is no cursor —
  the caller accumulates every id seen so far, so the URL grows unboundedly (~9 chars/id).
  With 700+ ids the URL exceeds CloudFront's limit and the appended response becomes a 414 error page. The already-rendered rows remain available, but infinite scrolling cannot recover in that page.
- To finish large lists, partition through member search: `?filter=all&q=<term>`. Each search has its own shorter `except_ids` list. Load each result set, merge by `data-member-id`, and stop when the union matches the group's reported result count.
- Filters: `?filter=all|admins|new|connections|recommended`

### Rate limiting — important
CloudFront blocks aggressive scrolling. ~90 load-more requests in ~2 minutes triggered it.
The blocked response is an HTML error page containing `"Request blocked"` /
`"Generated by cloudfront"` — it returns 200 and silently replaces content, so the member
count just stops growing. **Always test the response for those strings**, back off 60-120s,
and resume. A ~900ms scroll interval eventually trips it; profile fetches at concurrency 3
with a 400ms gap ran 738 requests with zero blocks.

### Member row selectors
```
.group-member-list__member-row        # one per member
  [data-member-id]                    # numeric member id (used for except_ids)
  a[href^="/<city-state>/<slug>"]     # profile link; slugs may contain literal `+`
  img                                 # business logo/avatar; alt = business name
```
Row `innerText` lines are ordered:
`[recommendation-count?, ownerName, "<business> <City>, ST", BADGES..., blurb, actions...]`

**Business name and city have no delimiter** ("Ambassador Five Cities Arroyo Grande, CA").
Don't regex them apart — derive the city from the profile URL slug (`/arroyo-grande-ca/...`)
and strip that suffix off the line. Verified: 191/216 names derived this way match the
profile's `og:title` exactly.

## Business profiles

URL: `/<city-state>/<business-slug>` (e.g. `/santa-maria-ca/vanessa-rae-media-2`)

Same-origin `fetch(url, {credentials:"include"})` returns the full authenticated HTML
(~150KB) and is far faster than navigating. `DOMParser` it and read:

| Field | Source | Coverage (738-member group) |
|---|---|---|
| Business name | `meta[property="og:title"]` → strip `" - Alignable"` then `" - <City>"` | ~100% |
| Logo | `meta[property="og:image"]` | 61% |
| Tags | `.business-tags a` (drop the `"Show all N"` entry) | 71% |
| Website | first non-alignable `a[href^="http"]` | **6%** |

- **No JSON-LD, no `__NEXT_DATA__`.** HTML parsing only.
- `og:image` falls back to a **placeholder** for logo-less businesses:
  `assets.alignable.com/assets/businesses/square_default_business-*.png`.
  Test for that substring — otherwise you'll count 100% logo coverage. Real logos decode
  from the base64 path segment to a key of `businesses/logos/...`.
- **Websites are genuinely rare (~6%)** — most members list none. This is not a scraping
  bug; profiles without one have no website element at all.
- Do not restrict profile-link slug matching to `[a-z0-9-]+`. Valid member slugs can contain
  literal `+`, such as `rogall-+-co`, `knife-+-fork`, and
  `build-your-nest-coaching-+-design-studio`.

## Data quality caveats

Members self-report, and the profile name can be a role rather than a business:
`/arroyo-grande-ca/placer-title-company` has `og:title` = **"Ambassador Five Cities"**
(the owner's Alignable ambassador title), while the blurb and tags are all Placer Title
escrow work. The URL slug is historical and does **not** track renames — `loanDepot` lives
at slug `mortgage-2`. Neither slug nor `og:title` is universally correct; `og:title` is what
Alignable itself displays. Expect to curate, not just scrape.

Tags are long-tail: 817 distinct tags across 207 businesses, max frequency 7. Frequency-based
category mapping does not work — score businesses against keyword sets instead.
